# v0.4.10 — Passwordless guest account

Released **14 November 2026**.

## Summary

The first slice of the v0.5.0 guest-experience milestone: a guest can sign in
with an email address and a single-use magic link, then see every reservation
tied to that address and open each one without hunting for the original
confirmation link.

## What's new

### Guest account at `/my-bookings/`

- `GuestLoginToken` stores only a SHA-256 hash of the raw token, the address,
  an expiry and a `used_at` marker.
- Tokens are single use and expire after `GUEST_LOGIN_MAX_AGE_MINUTES`
  (30 by default).
- The request page always returns the same neutral response; an email is only
  sent when the address already has at least one booking.
- Cache-backed cooldowns limit requests per email
  (`GUEST_LOGIN_COOLDOWN_SECONDS`, 300 by default) and per IP
  (`GUEST_LOGIN_IP_COOLDOWN_SECONDS`, 60 by default).
- Following the link stores the verified email in the session, rotates the
  session key and redirects to the booking list.

### Booking list and detail access

- The list shows every booking for the session email, newest stay first, with
  status, room and total.
- A signed-in guest can open `/booking/<REFERENCE>/` without a token. The view
  checks the session email against the booking's client email and then issues
  the booking's normal signed token, so confirm/modify/cancel keep using the
  existing token-gated API.
- Signing out clears the session; the booking lookup by reference + contact
  remains available.

### Email delivery

- `apps.hotel.email_providers` now accepts a provider-agnostic `EmailMessage`
  (recipient, subject, text/HTML bodies, attachments). SMTP, SES and Postmark
  all share the same interface.
- The magic-link email uses the configured provider and is localised into the
  guest's current language.

## Upgrade notes

1. Apply the migration:

   ```powershell
   .\.venv\Scripts\python.exe manage.py migrate
   ```

2. Optionally tune the new environment variables:

   ```text
   GUEST_LOGIN_MAX_AGE_MINUTES=30
   GUEST_LOGIN_COOLDOWN_SECONDS=300
   GUEST_LOGIN_IP_COOLDOWN_SECONDS=60
   ```

3. No cache-table change is required beyond the existing `createcachetable`
   step; the cooldowns use the default cache.

## Known limits

- The account lists bookings by exact email match (case-insensitive). Changing
  the email on a booking through reception moves it to the new address.
- There is no "resend link" button inside the email; requesting a new link is
  the retry path, and the cooldown applies.
- The guest list does not paginate yet; a pilot guest is unlikely to exceed the
  default page, but a long-stay repeat guest eventually will.
