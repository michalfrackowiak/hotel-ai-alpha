# v0.7.0 — operational visibility for confirmations and SMS

**Released:** 2026-11-19

## Summary

Reception can now trace confirmation delivery history and guest SMS replies, not just the latest status on a booking. Email delivery attempts are visible in `/ops/` and the admin, scheduler backlogs are covered by load tests, and SMS confirmations gain per-attempt history, provider delivery-receipt webhooks, and inbound reply capture.

## Changes

- **Email history in operations and admin** (PR #1)
  - `/ops/` shows the last 20 `EmailDelivery` attempts (newest first) with booking reference, recipient, subject, status, attempt and error.
  - Read-only `EmailDelivery` admin list with a subject column; the booking inline also shows the subject.
  - Provider webhook handling keeps the matching/latest delivery row in sync with the final status, so history remains append-only per attempt.
  - Tests cover send/retry rows, webhook sync by message id or latest row, webhooks with no delivery row, ops display in English and Polish, and admin read-only permissions.

- **Scheduler backlog coverage** (PR #2)
  - `tests/test_scheduler_load.py` covers 200 expired holds and 100 pending confirmation emails, confirming the scheduler backlog path completes within budget without scheduler code changes.

- **SMS delivery receipts and inbound replies** (PR #3)
  - New `SmsDelivery` model records each confirmation SMS attempt (provider, message id, recipient, body, status, error). `send_booking_confirmation_sms()` appends a delivery row for every sent/failed attempt and updates the booking's current SMS state.
  - `Booking.confirmation_sms_status` now includes `delivered` and `undelivered` in addition to `pending`, `sent` and `failed`.
  - New `InboundSmsMessage` model stores guest replies (sender/recipient, body, provider, provider message id, received time), linked to a booking when the sender's normalized phone number matches a recent booking.
  - New webhook endpoint: `POST /api/v1/sms/webhooks/<provider>/` (Twilio-shaped and generic payloads). If `SMS_WEBHOOK_SECRET` is set, callbacks must include the matching `X-Sms-Webhook-Secret` header. Delivery receipts match by booking reference or provider message id (booking field or `SmsDelivery`, falling back to the latest delivery) and update the booking and matching/latest delivery row; unknown receipts are acknowledged. Inbound replies are always stored and matched to a booking by phone when possible.
  - `/ops/` surfaces delivered/sent-awaiting/failure SMS counts, problem bookings, recent SMS delivery history, and recent inbound replies. The admin exposes read-only `SmsDelivery` and `InboundSmsMessage` lists/inlines on bookings.
  - Console SMS provider remains the offline default; Twilio is available when configured. There is no automatic SMS retry scheduler (reception can resend from the admin).

- **Configuration, docs and translations**
  - Added `SMS_WEBHOOK_SECRET` to settings and `.env.example`.
  - Updated `README.md`, `docs/API.md`, `docs/ARCHITECTURE.md`, `docs/PROJECT_MEMORY.md` and `docs/ROADMAP.md` for SMS receipts/replies, webhook auth/behavior, and delivery-history visibility.
  - Polish translations updated and compiled for new ops/admin copy.

## Upgrade notes

- Apply migrations: `python manage.py migrate`.
- To receive SMS delivery receipts and inbound replies, configure your provider callback to `POST /api/v1/sms/webhooks/<provider>/` (for example `twilio`) and set `SMS_WEBHOOK_SECRET` / send `X-Sms-Webhook-Secret` in production.
- SMS remains outbound-only in terms of automated retries: send failures never roll back a booking, delivery attempts are recorded, and reception can resend confirmations from the admin. Provider receipts and inbound replies are now captured when webhooks are configured.
- No existing email behavior is removed; email delivery continues to use the configured provider, retry/backoff scheduler path, and provider webhooks.
