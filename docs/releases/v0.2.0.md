# v0.2.0 — Operational confidence

Released **13 November 2026**. This release turns the v0.1.0 demo into something a pilot hotel can leave running: guests get a bilingual confirmation email, booking links can no longer be guessed, provider keys are encrypted, hold cleanup runs on a schedule and calendar drift can be found and repaired with one command.

## Highlights

- **Bilingual confirmation email** with a text body, HTML body and an `.ics` calendar attachment, sent after the booking commits in the guest's language.
- **Signed booking links** replace reference-only access. The API returns `manage_token` and `manage_url`; the web lookup issues a fresh link only when the guest supplies the reference plus the email or phone used to book.
- **Token-protected API** for booking detail, confirm and cancel (`token`, `X-Booking-Token` or Bearer). A guessed reference now returns `403 booking_access_denied`.
- **Encrypted provider keys**: `AIProvider.api_key` is Fernet-encrypted at rest, with a documented `rotate_provider_keys` command.
- **Persistent throttling**: DRF limits use the database cache, so they survive restarts and are shared by all gunicorn workers.
- **Scheduled hold cleanup**: a compose `scheduler` sidecar runs `expire_holds` every five minutes, with a cron/systemd alternative documented.
- **Calendar reconciliation**: `reconcile_calendars` reports missing, modified, failed, unsynced and stale events; `--apply` repairs them.
- **Email retries**: `send_booking_emails` resends confirmations that have no delivery marker.

## Upgrade notes

1. Run `manage.py migrate`. The migrations add `Booking.access_token`, `Booking.confirmation_email_sent_at` and re-encrypt any existing provider keys.
2. Run `manage.py createcachetable` once per database (the Docker entrypoint does this on boot).
3. Existing booking links that used only a reference stop working by design. Guests can request a fresh link at `/booking/` with their reference and email/phone.
4. Set `HOTEL_PUBLIC_URL` to the public origin so emailed links point at the right host.
5. Configure email with `EMAIL_BACKEND=smtp` and the `EMAIL_*` / `DEFAULT_FROM_EMAIL` variables. The default console backend only prints messages.
6. Set `FIELD_ENCRYPTION_KEY` to a long random value. If you change it later, set `FIELD_ENCRYPTION_KEY_OLD` and run `manage.py rotate_provider_keys`.
7. Start the new `scheduler` service with `docker compose up -d`, or add `expire_holds` to host cron/systemd.

## Known limitations

- Booking access is a signed link, not a guest account or password.
- Email uses SMTP/console backends; there is no bounce handling or delivery webhook.
- Calendar reconciliation repairs drift but does not import external bookings.
- Throttling uses SQLite through the database cache; a larger deployment should move to Redis.
- Single-container deployment; not sized for high concurrency or multi-tenancy.
- The demo policy remains rule-based; use a real provider for open-ended conversation.
