# v0.4.12 — Transactional email hardening

Released **14 November 2026**.

## Summary

The final v0.5.0 must-have. Confirmation emails now retry with exponential
backoff, provider-native bounce and complaint webhooks are normalised for SES
and Postmark, and reception gets an email delivery section on the operations
dashboard.

## What's new

### Retry with exponential backoff

- Each send attempt updates `confirmation_email_attempts`,
  `confirmation_email_last_attempt_at` and `confirmation_email_next_retry_at`
  on the booking.
- A failed attempt schedules the next try at
  `min(EMAIL_RETRY_BASE_SECONDS * 2^(attempts-1), EMAIL_RETRY_MAX_SECONDS)`.
- `send_pending_confirmation_emails()` only picks up bookings whose backoff
  window has passed and that still have attempts left
  (`EMAIL_MAX_ATTEMPTS`, 5 by default).
- The Docker `scheduler` sidecar now runs `send_booking_emails` alongside
  `expire_holds` and `reconcile_calendars --apply`.
- `send_booking_emails --force` remains the deliberate operator override.

### Provider-native bounce handling

- New `apps/hotel/email_webhooks.py` normalises three payload families:
  - SES events, including SNS-wrapped `Notification` messages
    (`notificationType`, `mail.messageId`, bounce diagnostic code).
  - Postmark webhooks (`RecordType`, `MessageID`, `Description`).
  - The existing generic `reference` / `event` shape.
- Webhooks match a booking by reference when present, otherwise by the stored
  provider message id. Unknown references return `404`; unknown message ids
  return `200 {"status": "ignored"}` so providers stop retrying.
- Confirmation emails now carry `booking_reference` metadata, which SES sends as
  a tag and Postmark as `Metadata`, giving the webhook a second lookup path.

### Delivery dashboard at `/ops/`

- New cards for delivered emails, email failures, bounced/complained messages
  and emails waiting to retry.
- A delivery table lists problem bookings with recipient, status, attempts,
  next retry and last error.
- The admin "Resend confirmation email" action now uses `force=True`, relies on
  the service to stamp delivery, and reports when nothing was sent.

### Polish catalogue

- New dashboard, model and admin strings are translated; the catalogue contains
  569 strings with 0 missing translations.

## Upgrade notes

1. Run `manage.py migrate`; migration `0010_booking_email_retry_fields` adds the
   retry fields to `Booking`.
2. Optional new environment variables: `EMAIL_MAX_ATTEMPTS` (5),
   `EMAIL_RETRY_BASE_SECONDS` (300) and `EMAIL_RETRY_MAX_SECONDS` (21600).
3. The scheduler sidecar now needs permission to run `send_booking_emails`; on a
   host without Docker add it to the same cron schedule as `expire_holds`.

## Known limits

- Backoff is per booking, not a shared queue; a very large backlog is processed
  serially by the scheduler command.
- SES attachments are still dropped by the v1 SendEmail path; the confirmation
  `.ics` therefore requires SMTP or Postmark. This is unchanged from v0.4.8.
- The dashboard shows delivery state, not a full per-message history; the
  append-only `BookingEvent` log remains the audit trail for booking state.
  Superseded by the v0.7.0 work: `/ops/` now lists per-message `EmailDelivery`
  rows.
