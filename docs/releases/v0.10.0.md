# v0.10.0 - Guest accounts and trusted self-service

**Released:** 2026-11-21

## Summary

Guests can now create a durable account, sign in securely, manage their profile, and review all bookings linked to their verified account from a unified `/my-bookings/` area in English and Polish. Existing signed booking links, reference+email/phone lookup, and transitional magic-link sign-in remain supported as secure fallbacks. The release adds targeted authorization, throttling, anti-enumeration, and account-linkage/coherence hardening across guest auth and booking access paths.

## Changes

- **Guest identity and account model** (PRs #16-#18)
  - Added `GuestAccount` linked to Django auth users and hotel `Client` records, with verified-email state and profile/contact fields kept consistent with `Client` where appropriate (migrations `hotel.0020_guest_account`, `hotel.0021_guest_email_verification`).
  - Guest accounts are separate from Django staff/admin accounts; staff users are excluded from guest flows.

- **Email/password registration, login and account security** (PRs #19-#25, hardening #26-#106)
  - Email/password registration, login, logout, password reset ("forgot password"), and secure password change flows.
  - Email verification/confirmation for new registrations and verified email changes, with anti-takeover/conflict guards across registration, email-change requests, verification consumption, and Google OAuth.
  - Strong Django password validation, CSRF-protected forms, cache-backed throttling/rate limiting, and neutral anti-enumeration responses for registration, login, magic-link, reset, verification, and lookup paths.
  - Guest booking reference+contact lookup is IP-rate-limited (`GUEST_BOOKING_LOOKUP_*`); throttled lookups return a neutral 429 response without performing lookup.

- **Google fast sign-in and linking** (PRs #22-#23)
  - Optional OAuth 2.0 / OpenID Connect "Continue with Google" sign-in/registration.
  - Account linking by verified email; conflicts are handled explicitly and safely (no cross-account takeover, including unverified-user-row permutations).
  - Configurable via `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` and public callback URL `${HOTEL_PUBLIC_URL}/my-bookings/google/callback/`; secrets never committed.

- **Unified My bookings and booking access** (PRs #24-#25, hardening #31-#106)
  - Authenticated `/my-bookings/` shows reservations linked to the guest's verified account/email(s), including status, dates, room/rate, payment/deposit summary, and a clear manage/detail path.
  - Bookings are linked to verified guest accounts in a backward-compatible way; existing and future bookings can be matched/linked by verified email. Phone-only bookings remain accessible via signed links and reference+phone lookup.
  - Preserved fallbacks: signed booking management links, reference+email/phone lookup, and transitional single-use magic-link sign-in.
  - Authorization remains explicit: guests can only access bookings they own; signed token/reference+contact rules remain in force for non-session access.

- **Coherence and security hardening** (PRs #31-#106)
  - Canonicalized guest booking visibility/access rules: authenticated and magic-link listing share `bookings_for_email` semantics; `guest_session_matches` and web guards enforce active non-staff verified-account boundaries and cross-account defenses.
  - Reference+contact lookup accepts verified-account associated emails and phones for same verified-account coherence while rejecting stored client emails owned by a different verified account.
  - Client-linkage/write guards prevent cross-account takeover: `link_clients_for_guest_account`, `find_or_create_client`, profile fallback client creation, and agent `send_confirmation_email` guard against overriding or leaking across different verified accounts; linkage refuses inactive/staff users.
  - Login/reset-confirm flows activate/verify/link verified guest accounts coherently; password reset requests can be delivered to inactive non-staff guests with usable passwords while keeping neutral responses.
  - Username collision hardening for email-change and registration; email-change and verification flows preserve account ownership boundaries.

- **UX, i18n, docs and config**
  - Guest-facing pages for register/login/logout/Google sign-in/password reset/password change/email verification/profile and bookings, consistent with site style and accessibility checks, in English and Polish.
  - `.env.example`, README, API, architecture, roadmap and project memory updated for guest auth/access settings and behavior.

## Migrations

- `hotel.0020_guest_account` - adds `GuestAccount` and guest-account/client linkage fields.
- `hotel.0021_guest_email_verification` - adds guest email verification state/token support.

## Configuration

Key guest auth/access settings (see `.env.example`):

- `GUEST_LOGIN_MAX_AGE_MINUTES`, `GUEST_LOGIN_COOLDOWN_SECONDS`, `GUEST_LOGIN_IP_COOLDOWN_SECONDS`
- `GUEST_EMAIL_VERIFICATION_MAX_AGE_MINUTES`, `GUEST_EMAIL_VERIFICATION_COOLDOWN_SECONDS`
- `GUEST_PASSWORD_LOGIN_WINDOW_SECONDS`, `GUEST_PASSWORD_LOGIN_MAX_ATTEMPTS_PER_EMAIL`, `GUEST_PASSWORD_LOGIN_MAX_ATTEMPTS_PER_IP`
- `GUEST_BOOKING_LOOKUP_WINDOW_SECONDS`, `GUEST_BOOKING_LOOKUP_MAX_ATTEMPTS_PER_IP`
- `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` (optional; callback `${HOTEL_PUBLIC_URL}/my-bookings/google/callback/`)

## Out of scope

- Replacing Django admin/staff authentication.
- Direct payment method storage or PCI-sensitive card-on-file handling.
- Cross-property/account federation beyond the single-hotel deployment model.
